### `taste-skill` vs `hallmark` — why not both on one build

These are the two "full pipeline" systems in the table above (the other 11 are narrower: a named aesthetic, an image-only workflow, or a non-code output format). Both take a vague brief and turn it into a complete, non-generic page — but through two incompatible mechanisms. Running both on the same build means two different logics both trying to decide the same things (what theme, what structure, what to do differently this time), and one will silently overwrite the other's decision.

| Axis | `taste-skill` | `hallmark` |
|---|---|---|
| **First move** | Infers a one-line "design read" from the brief itself (page kind, vibe words, audience) — asks the user only if genuinely ambiguous, and only one question | **Always** asks the user 3 questions (audience/use-case/tone) before writing anything, even on a fully-detailed brief — silence/"go ahead" triggers inference instead, but the ask happens first |
| **Style selection mechanism** | 3 numeric dials, `DESIGN_VARIANCE`/`MOTION_INTENSITY`/`VISUAL_DENSITY` (1–10 each), set from a signal→value lookup table | 20 *named* themes (Specimen, Atelier, Brutal, Bloom, …) in a catalog, or a custom-built OKLCH palette — no numeric dials at all |
| **Page structure** | No catalog of page shapes — structure emerges from a pile of individual hard rules (hero must fit in one viewport, max 2 consecutive image/text-split sections, bento cell-count must match content count, etc.) | Picks one of 21 *named* macrostructures (Bento Grid, Long Document, Manifesto, …) **first**, before any visual rule loads — the macrostructure decides hero/section/CTA shape as one bundled choice |
| **Existing-project awareness** | No pre-flight step — starts reasoning from the brief, doesn't read the project's current fonts/palette/spacing before proposing new ones | Step 0 always scans `package.json`/Tailwind config/CSS first and states what it found, then preserves those tokens by default |
| **Cross-build memory** | None — every invocation is judged independently, nothing is written to disk | Writes `.hallmark/log.json` after every build and **requires** the next build's macrostructure/theme/nav/footer to differ from the last 3–5 entries |
| **Named verbs** | None — one default flow only (an adjacent sibling skill, `redesign-skill`, covers the upgrade-existing-site case as a *separate file*) | `hallmark audit` (score only, no edits), `hallmark redesign` (in-place restructure), `hallmark study <url\|screenshot>` (extract another site's design DNA) |
| **Official design-system routing** | Has one: routes to Fluent UI/Material 3/Carbon/Primer/govuk-frontend/etc. when the brief matches an enterprise/public-sector pattern, native CSS otherwise | Has none — always produces its own catalog/custom look, never suggests installing a vendor design-system package |
| **Component-only mode** | Not distinguished from a full page | Has a dedicated Component-scope flow with different rules when the brief is one UI element, not a page |

**Concrete failure mode if you layer them**: say `hallmark` picks the *Lumen* theme, which pins the display font to Instrument Serif as one of its signature moves — but `taste-skill`'s own hard rule (§4.1) explicitly **bans** Instrument Serif as an LLM-favorite default. Follow both in the same build and you get a contradiction with no resolution rule, because neither skill knows the other exists. The same collision shows up structurally: `hallmark` commits to a macrostructure before any visual rule loads; `taste-skill` has no macrostructure concept, so there's nothing for `hallmark`'s pick to compose with — you'd be trying to run two different "what does this page's skeleton look like" decisions on the same output. And if you alternate between them across builds in the same project, `hallmark`'s diversification memory (`.hallmark/log.json`) never sees what `taste-skill` produced, so it can't actually enforce "different from last time" — the one mechanism that makes `hallmark` worth using for multi-page consistency silently stops working.

**Decision guide — pick one per project:**
- Want the **official-design-system routing** (the brief reads as enterprise SaaS, Shopify, a public-sector service, etc.) → `taste-skill` is the only one of the two with this capability.
- Building **many pages/many test variants in the same project** and need them to genuinely not repeat → `hallmark`'s `.hallmark/log.json` is the only mechanism here built for that; `taste-skill` has no memory across invocations.
- Need to **audit an existing site without editing it**, or **extract a look from a URL/screenshot** → both are `hallmark`-only (`audit`, `study`); `taste-skill` has neither.
- Upgrading an existing site rather than building greenfield → either `hallmark redesign` or the separate `redesign-skill` file — not `taste-skill`'s default flow, which assumes a fresh build.
- Otherwise (a single one-off landing page/portfolio, no existing project constraints, no multi-build consistency need) → either works; `taste-skill`'s brief-inference is lighter-weight (fewer mandatory questions), `hallmark`'s 58-gate slop test and named macrostructures are more prescriptive/heavier. Default to whichever the user names; if neither is named, `taste-skill` is the lower-friction default for a single build.

Pick `prototype-variants` for a live, flip-through comparison in one artifact; pick `sketch` for genuinely separate, individually-inspectable files with their own rationale docs.

## How to use this skill

1. **Producing a new deliverable** (banner, slide deck, logo, page-at-scale): start from the closest-matching domain's template/data rather than designing from a blank page — that consistency is the entire point of this category.
2. **Reviewing existing output**: `web-design-guidelines` and `writing-guidelines` are compliance-review domains, not generation domains — use them to audit, not to create.
3. **When multiple design domains could apply** (e.g. a slide deck needs both `slides` and `theme-factory` and `design-system` tokens), it's normal to pull from more than one — they're meant to compose.
4. Most design domains bundle real reference data (CSVs of palettes/fonts/charts, preset theme definitions, component templates) one level under their own directory — read those on demand rather than trying to hold the full database in context; that's why they're structured as references rather than inlined here.
5. **`brand` vs `anthropic-brand-guidelines`**: these sound similar but solve different jobs. `brand` helps *define or apply a brand system you're building* (any company's). `anthropic-brand-guidelines` applies one specific, already-fixed brand (Anthropic's) — reach for it only when the artifact is explicitly meant to carry Anthropic's look-and-feel, not as a generic "make this branded" request.
6. **`design` vs `brand`/`design-system`/`banner-design`/`slides`**: these all come from the same source package and deliberately overlap — `design` is the all-in-one entry point that bundles its own Logo/CIP/Banner/Icon/Social-Photo/Slides generation inline (one trigger, everything), while `brand`, `design-system`, `banner-design`, and `slides` are the same package's standalone, narrower versions of those individual pieces. Neither is more "correct" — pick `design` for a request spanning multiple deliverables or when unsure, pick the standalone skill when the request is for exactly one of those things and a smaller context load is preferable. Do not merge or treat one as deprecated; the duplication is intentional on the source package's part.
7. **Picking one taste system from the "Anti-AI-slop frontend taste systems" table**: these 13 sub-domains were read in full against each other and against `frontend-design`/`brand` — none turned out to be a true duplicate (each has its own concrete, largely incompatible rule set: different banned-font lists, different dial systems, different code skeletons), so all were kept as separate files with cross-references rather than merged. Pick by scope, not by reading every one:
   - Building a **full landing page/portfolio/redesign with actual code** → `taste-skill` (current) or `hallmark` — pick one, don't run both on the same build; see the "`taste-skill` vs `hallmark`" comparison above the table for which fits.
   - Want a **specific named aesthetic** rather than the general anti-slop pipeline → `brutalist-skill`, `minimalist-skill`, `soft-skill`, or `gpt-tasteskill` (motion-heavy Awwwards spec).
   - Already have an existing site to fix rather than a greenfield build → `redesign-skill` (or `hallmark redesign`).
   - Need **images, not code** → `imagegen-frontend-web` (one image per section), `imagegen-frontend-mobile` (app screens in device mockups), or `brandkit` (brand-guidelines boards/logo decks).
   - Working in **Codex** specifically and want it to generate reference images before writing code → `image-to-code-skill`.
   - Working in **Google Stitch** rather than a code-generating agent → `stitch-skill` (emits `DESIGN.md`, not code).
   - Need **exact backward compatibility** with an existing project already pinned to the original taste-skill behavior → `taste-skill-v1`.
8. **Not a design skill despite arriving in the same import**: the `taste-skill` source repo also bundled `output-skill` (anti-truncation / complete-output enforcement) — that's unrelated to visual design, so it was folded into `product-verification/references/output-skill` instead. Don't re-add it here.
9. **Animation/motion requests** ("build this animation", "review this transition", "audit our motion", "what's this effect called", "make this feel more alive"): go to the "Animation, motion & UI-decision tools" table above, not the taste-system table — these are mechanics (curves, springs, performance, gesture physics), not visual language. Pick by verb: build → `animate`, review a diff → `review-animations`, audit a whole codebase → `improve-animations`, find missing motion → `find-animation-opportunities`, name an effect → `animation-vocabulary`, gesture/spring physics specifically → `apple-design`, general polish philosophy or unsure where to start → `emil-design-eng`.
10. **Accessibility requests** ("is this accessible", "WCAG audit", "check a11y", "add alt text", "did my change break accessibility"): go to the "Accessibility auditing" table, picking by verb — whole site → `accessibility-audit`, one page automated → `accessibility-scan`, hands-on keyboard/screen-reader → `accessibility-inspect`, regression/CI gate → `accessibility-diff`, remediation → `accessibility-fix`. Connect the required MCP server(s) first (see that section's operational-requirement note) — these are not zero-dependency Markdown-only skills like most of this cluster.
11. **`design-md` vs. `stitch-skill` vs. `popular-web-designs`**: all three touch "how should this look," but at different layers. `popular-web-designs` supplies concrete visual vocabulary copied from a *specific real site*. `design-md` and `stitch-skill` both produce a design-token/description file rather than a rendered page, but for different consumers — see the disambiguation note under "Design reference catalogs & spec generators" above for the full comparison. Don't treat any pair here as duplicates of each other.
12. **Generative art / disposable sketch requests**: go to the "Generative art & disposable UI sketching" table above — pick `p5js` for advanced generative-art techniques or an actual exported file (video/SVG/high-res PNG), `algorithmic-art` for a lighter philosophy-guided sketch; pick `sketch` for separate-folder, individually-documented UI variants, `prototype-variants` for a live in-page picker across variants.
13. **Small fragments folded into existing files, added 2026-08-16 (see `SKILL-AUDIT.md`'s "2026-08-16（三）" section for the full extraction rationale)**: `frontend-design` gained an early "name the surface before designing" step (from hermes-agent's `claude-design`); `taste-skill` gained an optional §0.E "Creative reframing prompts" lateral-thinking nudge (from bencium.io's `bencium-impact-designer`); `hallmark`'s `audit` verb gained an alternate doc-grounded, phased mode for projects with `DESIGN_SYSTEM.md`/`APP_FLOW.md`/etc. already present (from bencium.io's `design-audit`); `redesign-skill`'s "Surface Upgrades" section had its glassmorphism recommendation flipped to a ban (per user decision, after finding it conflicted with bencium.io's `bencium-innovative-ux-designer`) — note that `hallmark` was deliberately **not** touched by that same flip; it still treats glassmorphism as contextually appropriate for an Apple-adjacent brand, and that tension was flagged, not resolved, per the user's explicit scoping.

## Note on scope

Marketing content-strategy skills (copywriting, ads, SEO audits, etc.) are deliberately **not** folded into this category even though some produce templated output — they're domain playbooks about *what to say*, not scaffolding for *how a deliverable is structured*, and remain as independent skills.
